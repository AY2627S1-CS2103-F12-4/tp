Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects from the model.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to an AddressBookParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a person).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

How the parsing works:

  • When called upon to parse a user command, the AddressBookParser class creates an XYZCommandParser (XYZ is a placeholder for the specific command name, e.g., AddCommandParser). The parser uses the other classes shown above to parse the user command and create an XYZCommand object (e.g., AddCommand). The AddressBookParser returns that object as a Command object.
  • All XYZCommandParser classes, such as AddCommandParser and DeleteCommandParser, implement the Parser interface so they can be treated similarly where appropriate, for example during testing.

Model component

API : Model.java

The Model component,

  • stores the address book data i.e., all Person objects (which are contained in a UniquePersonList object).
  • delegates participation management to the Mapper API. ModelManager owns a MapperManager, which links events and people using their stable IDs and exposes participation data through ReadOnlyParticipations.
  • stores the Person objects selected by the current filter, such as search results, in a separate filtered list. It exposes this list as an unmodifiable ObservableList<Person> that the UI can observe and bind to, so the UI updates when the list changes.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Note: The alternative, arguably more object-oriented, design below keeps a unique list of tags in AddressBook, and each Person references tags from that list. This lets AddressBook maintain one Tag object per unique tag instead of each Person holding its own Tag objects.

Storage component

API : Storage.java

The Storage component,

  • can save address book data, user preferences, and participations in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates participation data access to JsonParticipationStorage.
  • reconstructs a MapperManager by resolving the event and person IDs stored in each JsonAdaptedParticipation.
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

Common classes

Classes used by multiple components are in the seedu.address.commons package.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Participant search

Name and role searches share model state and the combined Events view:

Command Search type Predicate
search-participant NAME [/event EVENTID] [/include-archive] NAME ParticipantNameContainsKeywordPredicate
search-role ROLE [/event EVENTID] [/include-archive] ROLE ParticipationRoleContainsKeywordPredicate

Each parser normalizes query whitespace and validates the optional event ID, which must follow the search phrase. The standalone /include-archive flag, when present, must come last. Parsers remove that exact trailing flag before validating the remaining query and event scope. Repeated, misplaced, or unsupported options and flag values are rejected. SearchParticipantCommand calls the global or scoped Model#updateParticipantSearch overload; SearchRoleCommand calls the corresponding Model#updateParticipantRoleSearch overload. Each passes the includeArchived boolean. Both commands report registration and event counts and request the Events tab through CommandResult. Empty-result feedback distinguishes searches that include archives from default searches. Command equality and hash codes include archive visibility.

The following sequence diagram shows command execution for search-participant Michael /event E1 /include-archive, after parsing. It assumes that E1 exists and has at least one matching registration. events is the single-event list containing E1. Calls within the mapper and predicate are omitted for clarity. matchingEventPredicate represents the lambda that checks whether an event's ID belongs to matchingEventIds.

Without `/event`, the command calls the global overload, which searches across events; without `/include-archive`, archived events are excluded. Role search follows the same flow through `SearchRoleCommand`, `updateParticipantRoleSearch`, the `ROLE` search type, and `ParticipationRoleContainsKeywordPredicate`. An unknown scoped event raises `EventNotFoundException` before search state changes; the command converts it to `CommandException`. The diagram ends when the command returns its `CommandResult` to `LogicManager`; subsequent UI rendering is described below. `ModelManager` stores a transient `ParticipantSearchType`, normalized query, optional event ID, and `participantSearchIncludesArchived` boolean. An absent query means no active search. A present query with no event scope represents a global search, including when it has zero results. This state is independent of the selected event and is not persisted in storage. Starting either search type replaces the previous type, query, scope, archive visibility, and filter. Existing search overloads without the boolean delegate with `false`, preserving default exclusion of archived events. The shared `applyParticipantSearch` overloads resolve the scope, include archived events only when requested, and retrieve registrations through the mapper-backed `Model#getParticipationsForEvent`. Existing people and event display filters do not limit the search candidates. A nonexistent scoped event fails before changing search state; an archived scoped event yields no matches unless archives are included. Invalid input preserves the previous archive visibility as well as the query and results. Name matching normalizes whitespace in both the query and full name. Role matching uses a substring within any single assigned role. Both predicates ignore case. Each registration appears once, retaining all its roles, in event insertion order and then lexicographic Person ID order within each event. The model publishes the search type, scope, query, archive visibility, and matching-event filter before notifying observers of the result rows. `getParticipantSearchResults()` exposes a live, unmodifiable observable list through `Model` and `Logic`. `getParticipantSearchResultsForEvent(event)` returns an immutable snapshot matched by stable event ID. Consumers must reread it when the observable results change, even if the matching event IDs remain the same. `MainWindow` displays detailed feedback for both search commands and selects the Events tab. For a new search it selects the first matching event. Event selection uses `getParticipantSearchResultsForEvent` while a query is active, so the right pane contains only that event's matches. `ParticipantListPanel#showSearchResultsForEvent` displays those rows with the selected event's name, ID, and search phrase. Without an active query, ordinary event selection uses `Logic#getParticipationsForEvent` and displays all registrations for that event. `MainWindow` observes the result list to refresh per-event snapshots. During command execution, `isExecutingCommand` defers selection reconciliation until the model has finished publishing its filter and rows. `isUpdatingParticipantPanel` prevents programmatic selection changes from reentering that update. Refreshes retain the selected event by stable ID if it still matches; otherwise, they select the first remaining match. With no matches, selection and rows are empty while the panel retains the global or scoped query context. `Model` and `Logic` expose `isParticipantSearchIncludingArchived()`, which returns false when no search is active. `MainWindow` uses this value for the empty global-search heading: **All events** when archives are included and **All nonarchived events** otherwise. Scoped headings and event cards use `Event#getDisplayName()`, including its `` suffix. Participant cards show the stable Person ID, full name, and all assigned roles. Relevant model mutations refresh the active search using its stored type, scope, and archive visibility, including person updates, registration and role changes, event edits, and archive changes. Deleting an event during a global search refreshes the remaining matches. Deleting the scoped event calls `clearParticipantSearch()`, which clears either search type and restores the ordinary nonarchived event list. `ListEventCommand` calls `showEvents(includeArchived)` to clear the search and list events with the requested archive visibility. `clearParticipantSearch()` delegates to `showEvents(false)`; `FindEventCommand` uses this default reset before applying its name predicate. Both reset paths clear the stored search archive flag, even when the event listing includes archives. The UI clears the previous search rows and context after these resets, preventing a later command from reviving stale results. ### Participation mapping The participation mapping feature represents the many-to-many relationship between people and events. A person can participate in multiple events, while an event can have multiple participants. Each event-person pair has at most one `Participation` record. #### Model `Mapper` defines the API for adding, removing, querying and updating participations. `MapperManager` implements this API and is owned by `ModelManager`. Read-only access is exposed through `ReadOnlyParticipations`, which is also the boundary used by the storage component. A `Participation` is an immutable snapshot containing: * the associated `Event` and `Person`; * whether the person has been marked present; * event-specific `Tag` objects; and * event-specific `ParticipationRole` objects. Internally, `MapperManager` does not use mutable domain objects as map keys. It stores each record using the stable pair `(EventId, PersonId)` and keeps the attendance state, tags and roles as the value. When a query is made, it resolves the current `Event` and `Person` from `EventList` and `AddressBook` before returning an immutable `Participation` snapshot. This allows a participation to remain linked to a person after that person's details are edited. The mapper enforces the following invariants: * an event-person pair cannot be added twice; * both referenced entities must exist when a participation is added; * query results are unmodifiable snapshots; and * records whose event or person can no longer be resolved are not returned. `ModelManager` additionally removes all related participations when a person or event is deleted. Updates such as marking attendance or replacing event-specific tags create a new immutable state value rather than mutating an existing `Participation`. #### Adding a participation The sequence below shows the main interactions when `add-participant E1 P1 /role Facilitator /tag VIP` is executed. The parser converts each role and participant tag into its model type before constructing `AddParticipantCommand`. During execution, `ModelManager` resolves the supplied IDs. `MapperManager` validates the references again, rejects a duplicate event-person pair, and stores an initially absent participation with the supplied roles and tags. Failures are translated by the command into user-facing `CommandException` messages. The same mapper API supports the other participation operations. `mark-participant` replaces the stored state with one whose `isPresent` value is `true`, while `del-participant` removes the event-person pair. #### Displaying participants in the Events tab The Events tab displays `EventListPanel` and `ParticipantListPanel` together. `MainWindow` coordinates the selected event and obtains its participations through `Logic`. When the selected event changes, `MainWindow` passes the corresponding `Participation` objects to `ParticipantListPanel`. `ParticipantListPanel` creates a `ParticipantCard` for each participation. Each card displays the linked person's ID and name, participation roles, person tags, and event-specific tags. Edit and delete actions are passed back to `MainWindow`. #### Persistence Participations are stored separately in `data/participations.json`. Each `JsonAdaptedParticipation` stores only the event ID, person ID, attendance state, tags and roles; it does not duplicate the full event or person. At startup, people and events are loaded before participations. `JsonParticipationStorage` then resolves the stored IDs against the loaded `AddressBook` and `EventList` and constructs a `MapperManager`. Entries with invalid or unknown IDs are omitted, duplicate event-person pairs cause the participation file to be rejected, and invalid role or tag values are reported as data-loading errors. After a command executes successfully, `LogicManager` saves the current participations through the `ReadOnlyParticipations` interface. #### Design considerations **Aspect: How the event-person relationship is represented** * **Alternative 1 (current choice):** Store a composite `(EventId, PersonId)` key and resolve the domain objects when returning results. * Pros: Preserves the relationship when person details change; enforces one record per event-person pair; persistence stores compact, stable identifiers. * Cons: Queries require lookups in both source collections, and dangling references must be handled. * **Alternative 2:** Store `Event` and `Person` objects directly as map keys. * Pros: Simpler retrieval because no ID resolution is required. * Cons: Replacing or editing domain objects can leave stale references or make key equality unreliable. ### Cancelling participant attendance The `unmark-participant EVENT_ID PERSON_ID` command corrects an accidental check-in without removing the person's registration. The following sequence diagram shows the successful execution of `unmark-participant E1 P1` after parsing. `UnmarkParticipantCommand` calls `ModelManager#unmarkPresent`, which resolves the event and person by their stable IDs and checks that the participation exists and is currently present. `MapperManager#setPresent(event, person, false)` replaces the attendance state while preserving roles and tags. The model then refreshes any active participant search before the command returns a `CommandResult`. Missing events, people or registrations, and participants already marked absent, cause a `CommandException` with a specific error message; attendance is unchanged. These error paths and the mapper's internal ID resolution are omitted from the diagram for clarity. `LogicManager` saves the application data after successful command execution; those storage calls are also omitted. ### \[Proposed\] Undo/redo feature #### Proposed Implementation The proposed undo/redo mechanism is facilitated by `VersionedAddressBook`. It extends `AddressBook` with an undo/redo history, stored internally as an `addressBookStateList` and `currentStatePointer`. Additionally, it implements the following operations: * `VersionedAddressBook#commit()` -- Saves the current address book state in its history. * `VersionedAddressBook#undo()` -- Restores the previous address book state from its history. * `VersionedAddressBook#redo()` -- Restores a previously undone address book state from its history. These operations are exposed in the `Model` interface as `Model#commitAddressBook()`, `Model#undoAddressBook()` and `Model#redoAddressBook()` respectively. Given below is an example usage scenario and how the undo/redo mechanism behaves at each step. Step 1. The user launches the application for the first time. The `VersionedAddressBook` will be initialized with the initial address book state, and the `currentStatePointer` pointing to that single address book state. Step 2. The user executes `delete 5` command to delete the 5th person in the address book. The `delete` command calls `Model#commitAddressBook()`, causing the modified state of the address book after the `delete 5` command executes to be saved in the `addressBookStateList`, and the `currentStatePointer` is shifted to the newly inserted address book state. Step 3. The user executes `add n/David …​` to add a new person. The `add` command also calls `Model#commitAddressBook()`, causing another modified address book state to be saved into the `addressBookStateList`.
**Note:** If a command fails its execution, it will not call `Model#commitAddressBook()`, so the address book state will not be saved into the `addressBookStateList`.
Step 4. The user now decides that adding the person was a mistake, and decides to undo that action by executing the `undo` command. The `undo` command will call `Model#undoAddressBook()`, which will shift the `currentStatePointer` once to the left, pointing it to the previous address book state, and restores the address book to that state.
**Note:** If the `currentStatePointer` is at index 0, pointing to the initial AddressBook state, then there are no previous AddressBook states to restore. The `undo` command uses `Model#canUndoAddressBook()` to check if this is the case. If so, it will return an error to the user rather than attempting to perform the undo.

Similarly, how an undo operation goes through the `Model` component is shown below: The `redo` command does the opposite — it calls `Model#redoAddressBook()`, which shifts the `currentStatePointer` once to the right, pointing to the previously undone state, and restores the address book to that state.
**Note:** If the `currentStatePointer` is at index `addressBookStateList.size() - 1`, pointing to the latest address book state, then there are no undone AddressBook states to restore. The `redo` command uses `Model#canRedoAddressBook()` to check if this is the case. If so, it will return an error to the user rather than attempting to perform the redo.
Step 5. The user then decides to execute the command `list`. Commands that do not modify the address book, such as `list`, will usually not call `Model#commitAddressBook()`, `Model#undoAddressBook()` or `Model#redoAddressBook()`. Thus, the `addressBookStateList` remains unchanged. Step 6. The user executes `clear`, which calls `Model#commitAddressBook()`. Since the `currentStatePointer` is not pointing at the end of the `addressBookStateList`, all address book states after the `currentStatePointer` will be purged. Reason: It no longer makes sense to redo the `add n/David …` command. This is the behavior that most modern desktop applications follow. Archiving and restoring replace the event through `withArchived(boolean)` and `Model#updateEvent`, preserving its stable ID and registrations. `JsonAdaptedEvent` persists the flag; older event records without an archive field load as nonarchived. `Event#getDisplayName()` appends `` for display without modifying the stored name used for matching. The initial event view excludes archives. The overload `updateFilteredEventList(predicate, includeArchived)` combines archive visibility with the supplied predicate; its single-argument overload defaults to `false`. Search result collection uses the same archive policy so registration counts and displayed matching events agree. `list-event [/include-archive]` replaces the event filter through `showEvents(includeArchived)` and clears any participant search.
